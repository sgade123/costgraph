01Executive Summary

A cloud bill tells you what a service costs. It never tells you what one business outcome costs — one completed order, one API request, one successful AI decision — because the infrastructure producing that outcome is shared across products, spread across projects and teams, and increasingly includes AI/LLM spend measured in tokens, not dollars-per-order.

CostGraph is an open-source platform that ingests cost, telemetry, business, and AI-usage data through a pluggable connector layer, discovers how a product actually runs as a Business Value Graph, and computes the fully-loaded cost of a single business outcome — including its AI cost per successful outcome. It then explains why that cost changed and simulates optimizations that respect service-level and AI-quality guardrails.

The narrative in three verbs:

KNOW what one outcome costs → EXPLAIN why it changed and how each cost was attributed → OPTIMIZE toward a target unit cost without breaking quality or reliability constraints.

02Problem Statement

Unit economics in modern cloud + AI systems is unsolved for four structural reasons:

  1. Shared infrastructure. A GKE cluster, a Pub/Sub topic, or a Dataflow job serves several products at once. The bill is one number per service; splitting it per product is a judgment call, not a lookup.
  2. Cross-project / cross-team calls. A product's flow calls global services (fraud-check, payments) owned by other teams, in other projects. Their resource labels are common to every caller, so label-based attribution fails at the boundary.
  3. AI cost is outcome-opaque. LLM spend is metered per token and per model, with retries, tool calls, and caching. Cost per successful AI decision — and what happens to it when quality must stay above a threshold — is rarely surfaced by existing cost tools.
  4. No business denominator. Cost data lives in billing systems; the count of business outcomes lives in application systems. They are never joined, so "cost per order" cannot be computed from either alone.
Consequence: engineering leaders and finance can see total spend but cannot answer "what does one order cost to run, and why did it go up?" — the question that actually drives pricing, capacity, and optimization decisions.

03Solution Overview

CostGraph normalizes every input into four canonical data planes, then runs a deterministic engine stack over them:

COST

What each resource cost (billing exports, AI invoices), normalized to FOCUS-style line items.

TELEMETRY

Who consumed how much — the evidence used to split shared cost, carrying identity keys (labels, OTel baggage).

BUSINESS

How many outcomes were produced — the configurable denominator (orders, requests, AI decisions).

AI USAGE

Per-invocation LLM events with tokens, tool calls, retries, quality and success — enabling cost per successful outcome.

Above the planes sit five deterministic engines — attribution, unit economics, AI tokenomics, root-cause analysis, and optimization — and an AI agent that turns natural-language questions into engine calls and plain-language answers. The financial math is deterministic and auditable; the LLM only interprets and explains.

04System Architecture

A layered architecture: provider data enters through connectors, is normalized into the four planes, loaded by a repository, consumed by the engine stack, exposed via a REST API, and presented in a dashboard and to an agent.

07Attribution Model

The core intellectual work: splitting shared and cross-project cost to a product. Every attributed edge records which method produced its share and what evidence justifies it — so every number is auditable.

MethodWhen it appliesSplit key
dedicatedSole-owner resource100%
labelShared resource, same project, tagged per tenantResource label / namespace
consumptionShared compute (GKE)A telemetry measure — CPU request vs actual, memory, pods (the allocation policy)
message_attributeShared Pub/Sub topicPer-message source_app attribute
otel_baggageCross-project global servicesPropagated product baggage — the label is common to all callers, so identity must travel with the request
call_shareDownstream service computeProduct's share of calls, keyed by baggage
The hard case — cross-project attribution. When app1 calls a global fraud-check service in another team's project, that service's pods are labeled app: fraud-check — common to every caller — so a resource label cannot say who to bill. CostGraph attributes it by OpenTelemetry baggage: app1 stamps each request with product=app1, which propagates across the project boundary; the service counts CPU-seconds keyed by that baggage. app1's share of that work becomes its share of the service's cost. The allocation policy (request vs actual CPU) still governs how much of the service's compute is allocatable; the baggage governs app1's slice of it.

09Technical Specification

BACKEND

  • Python 3.12, FastAPI + Uvicorn
  • Pydantic v2 models = the four plane schemas
  • Connector framework: ABC contract + registry
  • Repository with lazy per-plane loading + caching
  • Deterministic engines (pure functions over planes)
  • LLM agent via provider API (interpretation only)

FRONTEND

  • React + Vite + TypeScript + Tailwind
  • Dashboard, value-graph view, tokenomics panel
  • Allocation-policy control, optimization simulator
  • Agent chat panel

OPS

  • Config-driven (costgraph.yaml)
  • Docker Compose for one-command local run
  • Deploy: Render/Railway (API) + Netlify/Vercel (UI)

Design principle — deterministic core, AI on top

All financial math is deterministic Python and unit-tested. The LLM never computes a number; it selects which engine to call and renders the result in prose. This makes outputs reproducible, auditable, and demo-stable.

Non-functional requirements

AttributeTarget
ReproducibilityIdentical inputs → identical financial outputs (no LLM in the math path)
AuditabilityEvery attributed edge carries method + evidence + confidence
ExtensibilityNew provider = one connector class; zero engine changes
OnboardingClone → configure → run on sample data in < 5 minutes
PortabilityNo dependency on any single cloud; file connector works offline

10API Surface

# Read
GET  /health

# Write / simulate
POST /api/allocation-policy               # {policy} → recompute everything
POST /api/optimize                        # {target_unit_cost, min_ai_success} → plan

# Agent
POST /api/agent/query                     # {question} → NL answer backed by engines

Example — the optimization request that is the platform's signature capability:

POST /api/optimize
{
  "product": "app1",
  "target_unit_cost": 0.055,
  "constraints": { "min_ai_success_rate": 0.95, "protect_prod": true }
}
// → ranked levers (model routing, cache, rightsizing) that hit the target
//   WITHOUT dropping AI success below 95% or mutating prod without approval

11Adoption Model

CostGraph is built to be cloned and used, not just demoed. Onboarding your own data is a config-and-connector task, never an engine change.

  1. Fastest path — file connector. Export your billing, telemetry, business metrics, and AI usage to JSON/CSV in the documented shapes; point costgraph.yaml at them; run.
  2. Live path — provider connector. Implement a fetch() that queries your source (BigQuery billing export, Cloud Monitoring, an orders DB, OpenAI usage) and returns normalized records; register it; reference it in config.
  3. Configure the business unit. Set unit_type to whatever outcome matters — order, request, AI decision — and the whole platform reports in those terms.
class MyGcpCostConnector(CostConnector):
    name = "gcp_billing"
    def fetch(self) -> list[CostRecord]:
        rows = query_bigquery_billing_export(self.project, self.month)
        return [self._normalize(r) for r in rows]   # map → CostRecord
